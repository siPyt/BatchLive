------------------
VERIFIED WORKFLOW: the described BatchLive operation has executable state
changes, regression evidence and live UI evidence. This does not imply that
every associated DeltaV application, dialog, file format or hardware behavior
is replicated.
PARTIAL: something related exists, but one or more required operations differ
or are missing. A substitute tag, decorative dialog, or checkbox is not parity.

FIRST VERIFIED IMPLEMENTATION PASS
----------------------------------

1. Controller description limit
   Source: p60, printed 1-59.
   Status: VERIFIED WORKFLOW for the length boundary.
   Controller creation accepts 255 characters and rejects 256.
   The creation input and engine use the same exported limit.
   Invalid names, excessive descriptions and duplicate controller names
   produce a diagnostic journal entry and explicit notification.
   Full descriptions remain available in the tooltip and wrap within their
   header, including an unbroken 255-character string.
   Other controller properties on this page are not all implemented.

2. Controller commissioning and optional auto-sense
   Source: pp55-67, especially p62 and the p67 exercise.
   Status: VERIFIED WORKFLOW within the current simulated controller model.
   Identify/Stop Identify, network redundancy, commission, address allocation,
   explicit I/O scan and five-minute cold restart are executable.
   Commissioning now offers Yes/No for auto-sense:
     Yes scans the controller's configured carrier/baseplate/channel inventory.
     No leaves the controller commissioned without performing a new scan.
     A standalone Auto-sense I/O action remains available later.
   Live verification on CTLR-01:
     - Identify indication appeared and stopped.
     - Network redundancy was saved during commissioning.
     - No kept lastAutoSense null and commissioned true.
     - Later auto-sense found 1 carrier, 3 baseplates and 18 channels.
     - Recommissioning with Yes performed the scan.
     - Cold Restart = 5 was applied and retained.
   Engine regression also verified restoration at the five-minute boundary.
   These addresses are simulated 192.0.2.x addresses, not real plant traffic.
   A newly created controller without carriers correctly scans zero channels.
   Remaining differences:
     - Physical Network panels, not Explorer drag/drop commissioning.
     - CHARM inventory, not the manual's traditional I/O cards.
     - No full node alarm/event-area, hardware-alarm or time-sync property model.
     - No real Windows/DeltaV logon or nonvolatile download script.

3. Defining plant areas
   Source: pp87-88, printed 2-16 through 2-17.
   Status: VERIFIED WORKFLOW for area creation and rename.
   Explorer supports Control Strategies -> New Area and area -> Rename.
   New Area creates an unused AREA1/AREA2/etc. and selects its editable name.
   Enter commits a valid rename; Escape leaves the current stored name.
   The course AREA_A prerequisite can be created without changing the existing
   pharma project's protected equipment or diagrams.
   Verified live procedure:
     create AREA_A -> rename PLANT_AREA_A -> create PLANT_AREA_B.
   A DI created through Explorer in PLANT_AREA_A retained that actual area.
   Area choices are shared by Control Module, Equipment Module and SFC forms.
   Renaming an occupied area atomically updates its control modules, equipment
   modules and SFCs; tags, I/O wiring, live values and references are preserved.
   Invalid/duplicate/missing names are rejected explicitly and journaled.
   Can Configure is required; OperatorA cannot perform these mutations.
   Existing project defaults remain; a New Project resets custom areas.
   Changes reside in the active project/session, like the existing plant model.
   No persistent configuration database/export is claimed.
   Updated exercise IDs prevent old area-viewing checkmarks from appearing
   to complete this new create/rename exercise.

4. Previous / Next picture navigation
   Source: pp134-136, printed 3-29 through 3-31.
   Status: VERIFIED WORKFLOW for configuration and navigation.
   In Display Builder Configure, Previous Picture or Next Picture opens the
   shared picture-link properties. Apply Links validates and stores both links.
   In Run:
     Ovw_ref.grf navigates to the actual Overview.
     alarmList.grf navigates to the actual Alarm List.
     A created picture name navigates to that builder picture without leaving
     Run mode. Names are case-insensitive with an optional .grf suffix.
   Blank fields remove links. Reciprocal links are not fabricated.
   Can Configure is required to apply navigation settings.
   Missing targets are rejected without partially applying the other link.
   Deleting a linked target makes subsequent navigation fail explicitly.
   No fake .grf file is loaded and no decorative-only navigation is claimed.
   Live verification followed both course aliases and a second custom picture.
   Remaining differences:
     - BatchLive builder, not DeltaV Operate/iFIX main-template creation.
     - Links are active-session picture metadata, not native .grf files.
     - No native picture save/export, grouped main-template objects, or
       course-identical application menu/keyboard workflow is claimed.
